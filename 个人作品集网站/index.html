智行 · 多 Agent 智能旅行规划助手

我的角色：独立设计与开发 · 个人项目（2025.02 – 2025.06）

S 背景

在龙山乡实习时发现，游客做行程规划要跨五六个平台查开放时间、门票和交通，而通用大模型给的攻略"看着完整却不可执行"——景点已停业、预算超支、一天排八个景点的情况比比皆是。

T 难点

独立完成架构设计与开发。最难的点：让大模型输出从"一段建议文本"变成"可执行、可验证、出错能回退"的流程；工具调用失败或结果不准时，系统不能把错误一路带进最终行程。

A 方案

用 LangGraph StateGraph 编排"理解→规划→搜索→预算→审查"五个节点，智能体通过共享 State 协同——选图结构而非单条 Prompt，是因为流程需要显式回退与熔断，且控制流在 LangSmith 中可观测；搜索节点用 ReAct 子图自主调用 Tavily 联网搜索与本地旅行知识库（上限 5 轮迭代）；规划与审查均用 Function Calling 约束结构化输出，审查不通过则带着反馈回退规划节点、3 次熔断；工具封装为独立 MCP Server（stdio），注册进 Cursor / Claude Desktop 后 AI 可自主调用。踩坑：Function Calling 只保证参数结构合法、不保证字段填全，JSON 仍可能截断——所有节点强制 try-catch，连续两次解析失败直接报错终止，绝不带坏数据进入搜索。

R 成果

25 条端到端测试用例规划成功率 88%；ReAct 的"观察报错→换词重试"自我纠错使工具调用成功率 85% → 93%；自研 MCP 工具在 Cursor 中被 AI 自主调用完成真实旅行查询。

L 复盘

两条最深的教训：一是"偏好是参考权重、不是硬过滤"，规划智能体按偏好优先级平衡安排，审查只查覆盖度；二是"能代码做的别让大模型做"——预算累加用代码、城市档位参考价用硬编码表，大模型只负责分类。如果重来，搜索节点会从串行 ReAct 改为并行分槽检索加短期结果缓存，那是全链路最慢最贵的一环。

健康档案智能数据质量检测系统 · LLM + 规则引擎混合架构

我的角色：东软实习 · 独立设计、开发并交付（2026.07 – 2026.08）

S 背景

康养平台 7 类评估档案靠人工抽检：数值越界这类问题规则能查，但"生活完全能自理，护理级别却填了卧床"这类跨字段语义矛盾，规则写不全、人工也容易漏。

T 难点

实习中独立交付。最难的点不在"让大模型会查错"，而在"大模型不可靠时系统怎么办"——它可能超时、可能没配 Key、可能误判，检测流水线不能因为它挂掉就停转。

A 方案

设计三层流水线：统计清洗（IQR + IsolationForest）→ Qwen2.5 大模型业务校验（每批 15 条，Prompt 内含 Schema 与 few-shot 示例）→ YAML 声明式规则引擎。关键决策是把规则引擎同时用作兜底和对比基线：dashscope SDK 不支持超时参数、调用可能无限阻塞，就用守护线程 join(60s) 包裹，超时或无 Key 自动降级规则引擎；"规则 vs 大模型"对比看板量化两类能力的边界。Schema 驱动设计下，大模型校验和规则引擎读同一份 YAML，新增档案类型只写配置不动代码。

R 成果

2000 条真实档案检出异常约 175 条，其中大模型额外检出语义矛盾约 25 条（占 14%），规则全部漏检；大模型故障导致的流水线卡死率 20% → 0；单批 15 条平均约 5 分钟；新增档案类型配置从 1 天缩短至 1 小时（提效约 90%）。

L 复盘

最大的认知升级：大模型在系统里应该是"能力增强层"而不是"单点依赖"，上线前先问"它挂了怎么办"。每批 15 条是在上下文长度与调用次数之间实测出的平衡点。如果重来，会给大模型的检出结果加置信度与二次复核机制，而不是直接采信。

医助通 · 基于 RAG 的智能医疗导诊系统

我的角色：东软实习 · 主负责 RAG 全链路（2025.08 – 2026.07）

S 背景

基层医疗咨询场景里，通用大模型的幻觉是不可接受的风险——编造药品名、剂量，而且回答没有来源可追溯。

T 难点

主负责 RAG 全链路。最难的点：医疗场景对准确性零容忍，检索不到相关内容时模型倾向于"硬答"，必须从检索、生成到安全拦截多层设防。

A 方案

基于 ChromaDB 构建医学知识库：文档解析 → 切片（块大小 200）→ 通义千问 Embedding → BM25+向量混合检索（RRF 融合）→ Cross-Encoder 二次精排。选混合检索是因为纯向量对药名、检查项这类精确关键词召回弱，BM25 补精确匹配；医疗 System Prompt 支撑多轮问诊，SSE 流式输出 + Redis 双层缓存；用 LLaMA-Factory 对 Qwen 做 LoRA 微调（rank=8, alpha=16）统一问诊风格与输出格式。踩坑：Embedding 模型必须与聊天模型同厂商——最初用 OpenAI 的 embedding 配 Qwen，向量空间不一致导致检索结果全乱，统一为 DashScope text-embedding-v3 后恢复；急症、自伤倾向等安全拦截用关键词代码实现，不经过大模型。

R 成果

混合检索Top-3 召回率 88%（纯向量仅 73%）；LoRA 微调后输出格式合规率 65% → 88%；SSE 首字延迟 1.6 秒；Redis 缓存使重复问答响应 8s → 3s。

L 复盘

教训：RAG 的效果瓶颈往往在检索而不在生成，先把召回率量化清楚再调 Prompt；安全相关判断永远走代码。如果重来，切片会按文档语义结构切而不是固定长度，并增加答案与引用来源的对齐校验。

医疗文本数据工程与推理服务化

我的角色：东软实习 · 独立负责数据工程与推理服务（2025.08 – 2026.07）

S 背景

医疗文本多标签分类任务拿到 9762 条原始标注文本，标签字段格式混乱——多标签挤在一个字段里、同一标签多种写法、标记噪声多，直接拿去训练不可行。

T 难点

独立负责数据工程与推理服务化。最难的点：没有现成标注规范，清洗规则要自己从脏数据里一条条归纳。

A 方案

用 Python + Pandas 构建 ETL 流程：正则解析多标签字段、标签别名归一、两级去重，沉淀出 12 类标签体系并按 6:2:2 划分；推理服务用 Config 统一配置、CPU/GPU 自适应切换；搭建 Hamming Loss / AUC / 逐标签 P-R 多维评估模块与阈值寻优机制。

R 成果

9762 条原始样本清洗为 2844 条高质量数据（剔除约 70% 噪声与重复），支撑后续 BERT 多标签分类的训练与评估。

L 复盘

教训：数据质量决定模型上限，归纳清洗规则比调模型参数更花时间。如果重来，会把清洗规则沉淀成可配置、可复用的断言库，让新项目直接复用而不是重写。

智瞳 · CV 感知 + LLM 决策课堂督导系统

我的角色：个人项目 · CV 管线与 LLM 决策层（2024.10 – 2024.12）

S 背景

课堂督导靠老师巡堂，瞌睡、走神发现滞后，全班注意力状态也无法量化留存。

T 难点

个人独立项目。最难的点：实时视频流上既要跑检测又要控制延迟，而且检测结果不能只是一堆数字，得变成老师能直接用的教学建议。

A 方案

用 OpenCV + ONNX Runtime 搭级联推理管线，RetinaFace 人脸检测与 ShuffleNetV2 关键点均为预训练模型转 ONNX 部署（不自行训练）；瞌睡判定用 EAR 眼睛开合比 + 滑动窗口的工程阈值，而不是再训一个分类模型；行为时序数据结构化后送入 Qwen，输出注意力衰减分析与个性化干预策略；并提供自然语言查询接口（如"今天哪些学生注意力最差"），大模型解析意图后查询数据库生成报告——与 Agent 工具调用同源的 Text2SQL 思路。

R 成果

跑通"实时检测 → 行为入库 → 大模型分析 → 自然语言查询"完整闭环，课堂场景下可稳定给出瞌睡预警与干预建议。

L 复盘

教训：预训练模型工程化落地的核心是管线编排与阈值工程，不是自己造模型；真正让系统从"能报警"变成"能给建议"的是 LLM 决策层。如果重来，CV 部分会换更轻的端侧模型，把精力更多投在决策层的 Prompt 评估上。
